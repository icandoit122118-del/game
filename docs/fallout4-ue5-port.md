# 폴아웃 4를 언리얼 엔진 5로 이식하면 무엇이 좋아지는가

> 대상: 게임 개발자 / 기술 기획자 / 모더
> 비교 축: **Creation Engine (Fallout 4, 2015)** vs **Unreal Engine 5 (5.4~5.6대)**

---

## 0. 3줄 요약

1. **그래픽·애니메이션·오디오·툴링은 세대가 통째로 바뀐다.** Lumen/Nanite/Virtual Shadow Maps, Motion Matching, MetaSounds, World Partition 등 지난 10년치 기술이 한 번에 들어온다.
2. **폴아웃 4의 가장 큰 고질병인 "다운타운 보스턴 CPU 병목"과 "프레임에 묶인 물리"가 구조적으로 해결된다.** 이건 그래픽보다 체감이 크다.
3. **하지만 "이식(port)"이 아니라 사실상 "풀 리메이크"다.** Creation Engine의 진짜 무기인 *월드 전체 오브젝트 영속성(persistence)* 과 *ESP/ESM 모드 레이어링*은 UE5에 기본 제공되지 않으며, 10년치 모드 생태계는 전부 무효화된다. 현실적인 답은 **하이브리드**(오블리비언 리마스터드 방식)다.

## 1. 렌더링 / 그래픽

### 1-1. 조명 — 가장 큰 변화

| 항목 | Fallout 4 (Creation Engine) | Unreal Engine 5 |
|---|---|---|
| 전역 조명(GI) | 베이크된 라이트맵 + 이미지 기반 라이팅. 실내는 수작업 배치 | **Lumen** — 완전 동적 GI, 실시간 바운스 |
| 반사 | 큐브맵 + 저품질 SSR (화면 밖은 그냥 사라짐) | Lumen Reflections / 하드웨어 레이트레이싱 |
| 그림자 | 캐스케이드 섀도우 맵, 짧은 거리, 깜빡임/계단현상 | **Virtual Shadow Maps** — 전 거리 고해상도 일관성 |
| 동적 광원 수 | 매우 제한적 (성능 급락) | **MegaLights** — 수천 개 동적 광원 실용화 |
| 볼류메트릭 | NVIDIA Godrays(고비용, 구식) | 볼류메트릭 포그 / 볼류메트릭 클라우드 |
| 레퍼런스 렌더 | 없음 | **Path Tracer** 내장 (포토모드·마케팅 컷) |

**폴아웃 4 맥락에서의 실익:**
- 핍보이 화면, 손전등, 화염, 플라스마·레이저 탄, 네온 간판이 **주변을 실제로 밝힌다.** 현재는 전부 가짜 광원이거나 아예 반응이 없다.
- 지하철·볼트·창고 같은 실내가 수작업 라이트 배치 없이도 물리적으로 맞는 그늘을 갖는다.
- 보스턴 스모그·먼지·안개를 통과하는 빛줄기(볼류메트릭)는 폴아웃 특유의 분위기와 궁합이 극단적으로 좋다.
- **핵폭발/방사능 폭풍의 실시간 라이팅 변화**가 월드 전체에 즉시 반영된다.

### 1-2. 지오메트리 — Nanite

폴아웃 4의 고질적 문제인 **LOD 팝핑**(멀리서 건물이 뭉개지고, 가까워지면 갑자기 바뀌는 현상)과 저폴리 원경이 사라진다.

- Nanite는 가상화된 마이크로폴리곤 지오메트리 — LOD를 **수작업으로 만들 필요가 없다.**
- 폴아웃 4는 잡동사니(clutter)로 이루어진 게임이다. 무너진 건물, 잔해 더미, 쓰레기, 파이프. 이건 Nanite가 가장 잘하는 영역이다.
- 원경 건물이 실제 메시 그대로 보인다 → 보스턴 스카이라인의 인상이 완전히 달라진다.
- UE 5.5+에서 **Nanite Foliage / Nanite Skeletal Mesh**가 추가되어 나무·풀·캐릭터까지 커버 범위가 넓어졌다.
- Nanite Tessellation(5.4+)으로 지형·잔해에 실제 변위(displacement)를 줄 수 있다.

> ⚠️ 주의: Nanite는 마스크드/투명 머티리얼과 소형 인스턴스 대량 배치에서 비용이 붙는다. 만능은 아니다.

### 1-3. 텍스처 / 업스케일링 / 출력

- **Virtual Texturing** — 텍스처 팝인 감소, VRAM 예산 효율화
- **TSR** 기본 탑재 + DLSS / FSR / XeSS 플러그인 — 폴아웃 4는 흐릿한 TAA 하나뿐이고 업스케일러가 없다
- **네이티브 HDR 출력** — 폴아웃 4는 사실상 없다(모드로 억지 구현)
- 최신 톤매핑, 물리 기반 카메라 노출, 정상적인 DOF/모션블러

### 1-4. 캐릭터 표현

- **스트랜드 기반 헤어** — 폴아웃 4의 머리카락은 2015년 기준으로도 혹평받은 부분이다
- 제대로 된 **피부 서브서피스 스캐터링**, 눈 셰이더
- **MetaHuman + MetaHuman Animator** — 영상 기반 얼굴 퍼포먼스 캡처. 대화 카메라가 얼굴을 클로즈업하는 게임에서 이건 결정적이다
- **Chaos Cloth** — 코트, 볼트슈트, 깃발, 넝마가 실제로 흔들린다

### 1-5. 물 / 대기

- UE5 Water System — 파도, 코스틱스, 얕은 물 상호작용
- 폴아웃 4의 물은 사실상 평면 + 노멀맵 수준

## 2. 성능 / CPU 아키텍처 — **가장 저평가된 이득**

폴아웃 4에서 RTX 5090을 꽂아도 **다운타운 보스턴에서 프레임이 무너지는** 이유는 GPU가 아니다. CPU다.

### 2-1. 멀티스레딩

| 항목 | Fallout 4 | UE5 |
|---|---|---|
| 렌더 스레드 | 사실상 단일 스레드 병목 | 병렬 커맨드 리스트 생성, Task Graph |
| 그래픽 API | **DirectX 11 전용** | DX12 / Vulkan / Metal |
| 드로우콜 | 매우 높음 → CPU 한계 | Nanite의 GPU 드리븐 렌더링으로 붕괴시킴 |
| 스크립트 VM | Papyrus (단일 스레드, 지연 기반, 느림) | C++ / Blueprint, Mass Entity 병렬 처리 |
| 로딩 | 동기 로딩 다수 | 비동기 스트리밍 기본 |

**결과:** 다운타운 보스턴 / 대형 정착지 / 대규모 전투에서의 프레임 드랍이 구조적으로 개선된다.

### 2-2. 프레임레이트에 묶인 물리 — 해방

폴아웃 4는 Havok 물리가 프레임레이트에 결합되어 있다. **60fps를 넘기면 물리가 깨진다.**
- 오브젝트가 날아가고, 터미널·자물쇠따기 속도가 이상해지고, 엘리베이터가 오작동
- 그래서 `iPresentInterval` 모드나 프레임 제한이 사실상 필수

UE5의 **Chaos**는 렌더 프레임과 독립된 고정 서브스텝으로 돌아간다.
→ **144Hz / 240Hz 모니터에서 그냥 정상 작동한다.** 이것만으로도 이식 명분이 된다.

### 2-3. 스터터

- 폴아웃 4: 셀 경계 통과 시 하드 히칭, 실내외 전환 로딩
- UE5: World Partition 스트리밍 + PSO 프리캐싱(5.2+)

> ⚠️ 단, UE5는 **셰이더 컴파일 스터터**와 **트래버설 스터터**로 악명이 높다. 제대로 안 만들면 오히려 나빠질 수 있다. 공짜가 아니다.

## 3. 월드 스트리밍 / 레벨 구조

폴아웃 4는 `uGridsToLoad` 기반 셀 그리드 + **실내/실외 완전 분리 + 로딩 도어** 구조다.

UE5에서 바뀌는 것:

- **World Partition** — 그리드 기반 자동 스트리밍, 셀 개념 자체가 사라짐
- **로딩 화면 없는 실내 진입** — 문 열고 그냥 들어간다 (실내를 같은 월드에 배치할 경우)
- **Data Layers** — 퀘스트 진행에 따른 월드 상태 변화(폐허 → 재건된 정착지)를 레이어 스왑으로 처리
- **Level Instancing** — 베데스다 특유의 모듈러 키트배싱 워크플로와 궁합이 매우 좋음
- **자동 HLOD 생성** — 폴아웃 4의 악명 높은 **precombined meshes / previs** 수동 베이크를 대체

> 💡 **모더에게 특히 중요:** 폴아웃 4에서 셀 하나만 건드려도 precombine/previs가 깨지면서 그 지역 성능이 반토막 나는 문제가 있다. HLOD 자동화는 이 문제 자체를 없앤다.

## 4. 애니메이션

폴아웃 4의 애니메이션은 Havok Behavior 기반이며 뻣뻣하기로 유명하다.

| 문제 | UE5 해법 |
|---|---|
| 발 미끄러짐(foot skating) | **Motion Matching** (5.4+), Distance Matching |
| 경사면에서 발이 뜸 | **Full Body IK**, 풋 플레이스먼트 IK |
| 전환이 뚝뚝 끊김 | Layered Blend per Bone, Pose Search / Chooser |
| 절차적 조정 불가 | **Control Rig** — 런타임 리깅 조작 |
| 조준/무기 정렬 부자연스러움 | Aim Offset + IK 조합 |
| 사망 래그돌이 코믹하게 날아감 | Chaos Physical Animation, 물리 블렌딩 |
| 립싱크가 죽은 눈 | **MetaHuman Animator**, ARKit 블렌드셰이프 |

NPC가 걷고, 앉고, 문을 열고, 총을 드는 모든 동작이 "게임 캐릭터"가 아니라 "사람"처럼 보이기 시작한다.

## 7. AI / 게임플레이 시스템

### 7-1. 스크립팅

**Papyrus는 느리다.** 단일 스레드, 지연 큐 기반이라 스크립트가 밀리면 퀘스트가 멈추거나 이벤트가 유실된다. 모드를 많이 깔면 "스크립트 랙"이 생기는 게 이 때문이다.

UE5: C++ / Blueprint. 실행 속도 차이가 수십~수백 배 수준이다.

### 7-2. AI

- **Behavior Tree + EQS(Environment Query System)** — 엄폐물 선택, 전술적 포지셔닝이 실제로 가능
- **StateTree** — 상태 기반 AI를 계층적으로 관리
- **Smart Objects** — NPC가 환경 오브젝트와 상호작용하는 걸 데이터로 정의 (베데스다의 AI 패키지 개념의 현대판)
- **Mass Entity (MassAI)** — 수천 NPC 군중 시뮬레이션. 다이아몬드 시티가 12명이 아니라 진짜 도시가 될 수 있다

### 7-3. 내비메시 — 정착지 문제의 해결

폴아웃 4의 유명한 버그: **정착지에 건물을 지으면 동료와 NPC가 끼거나 못 지나간다.** 플레이어 건축물에 대해 내비메시가 제대로 재생성되지 않기 때문이다.

UE5는 Recast 기반 **런타임 동적 내비메시 재생성**을 지원한다. 이 문제가 구조적으로 사라진다.

## 8. UI

폴아웃 4의 UI는 **Scaleform (Adobe Flash / ActionScript)** 기반이다. Flash는 2020년에 사망했다.

- 해상도 독립적이지 않음 → 울트라와이드에서 UI가 깨짐(모드 필수)
- 4K/8K 스케일링 문제
- 모딩 난이도 높음 (SWF 편집)

UE5의 **UMG / CommonUI / Slate**:
- 해상도·종횡비 독립
- 21:9 / 32:9 / 가변 주사율 네이티브 지원
- 게임패드 포커스 내비게이션 기본 제공
- **접근성**: 자막 크기 조절, 색맹 모드, UI 스케일링, 스크린 리더 훅
- 핍보이를 **실제 3D 월드 위젯**으로 렌더링 + CRT 셰이더 → 몰입도 상승

## 9. 네트워크 / 협동 플레이

폴아웃 4에는 멀티플레이가 없다. 폴아웃 76은 이걸 위해 엔진을 대대적으로 뜯어고쳤고, 넷코드 문제로 오래 고생했다.

UE5는 **성숙한 리플리케이션 시스템**을 기본 제공한다 (5.1+의 **Iris**는 대규모 리플리케이션 대응).

→ **협동 플레이가 현실적인 선택지가 된다.** 다만 폴아웃 4의 일시정지형 V.A.T.S.와 대화 시스템은 재설계가 필요하다.

## 11. 개발 파이프라인 / 툴링

| 항목 | Creation Kit | Unreal Editor |
|---|---|---|
| 안정성 | 크래시 잦음, 구식 UI | 상대적으로 안정 |
| 반복 속도 | 재시작 필요한 경우 많음 | Live Coding, Blueprint 핫 리로드 |
| 에셋 포맷 | NIF / BA2 (독자 포맷) | FBX / glTF / USD 표준 |

## 12. ⚠️ 잃는 것 / 리스크 — 여기가 핵심

이 부분을 빼면 답변이 절반짜리다.

### 12-1. **오브젝트 영속성 (Object Persistence)** — 가장 큰 손실

Creation Engine의 진짜 무기는 그래픽이 아니다.
**월드의 모든 오브젝트가 개별 상태를 가지고 세이브에 저장되는 시뮬레이션 모델**이다.

- 커피잔을 바닥에 떨어뜨리고 → 50시간 후 돌아오면 → **그 자리에 그대로 있다**
- 시체, 소유권, 인벤토리, 물리 상태, 스크립트 변수까지 전부 개별 추적
- 이게 "베데스다 게임 느낌"의 정체다

**UE5에는 이런 게 없다.** 액터는 기본적으로 레벨 로드 시 초기 상태로 리셋된다.
→ 영속성 레이어를 **처음부터 직접 설계·구현해야 한다.** "UE5로 옮기면 되잖아"가 순진한 이유가 이것이다.

### 12-2. 모드 생태계 전멸

- 10년, Nexus 기준 수만 개의 모드
- **F4SE**(Script Extender), 그에 의존하는 대형 모드들
- ESM/ESP **레코드 오버라이드 기반 모드 레이어링** — 여러 모드가 같은 데이터를 계층적으로 덮어쓰고 충돌을 해소하는 이 구조는 사실 매우 우아하다. UE5의 에셋 시스템에는 대응물이 없다
- Fallout London, Sim Settlements 같은 대형 프로젝트 전부 무효

> 참고: 폴아웃 4의 2024년 "넥스트젠 업데이트"는 성능 개선이 미미했던 반면 모드를 대거 파손시켜 커뮤니티에서 혹평받았다. 엔진 교체는 그것의 100배 규모 사건이다.

### 12-3. 하드웨어 요구사항 상승

- 폴아웃 4는 저사양 PC에서도 돌아간다
- Lumen + Nanite는 기준 하드웨어를 크게 올린다
- **어설프게 만든 UE5 포팅은 원본보다 더 무겁고 더 끊길 수 있다** (셰이더 스터터, 트래버설 히칭)

### 12-4. "이식"이 아니라 "리메이크"

옮겨야 하는 것:
- 게임플레이 코드 전체 (수백만 줄 규모)
- 퀘스트·대화 데이터 (음성 11만 라인 이상), AI 패키지, 팩션 관계
- 정착지 건설 시스템, 무기 개조, 파워아머, V.A.T.S., 크래프팅
- Creation Kit의 레코드 데이터 모델 전체

현실적 규모: **4~6년, 200명 이상.** 폴아웃 4 원작 개발 규모와 비슷하거나 그 이상이다.

### 12-5. 법적 현실

베데스다/마이크로소프트만 할 수 있다. 팬 프로젝트는 에셋 사용 시 즉시 중단 통보 대상이다.
(유튜브의 "Fallout 4 in UE5" 영상들은 환경 리크리에이션 데모지, 이식이 아니다.)

# 부록 A. 오브젝트 영속성의 작동 원리 (심층)

12-1절에서 "UE5에 대응물이 없다"고 한 그 시스템이 실제로 어떻게 돌아가는지.

## A-0. 한 줄 요약

> **세이브 파일은 월드의 스냅샷이 아니다. ESM(원본 데이터) 대비 "차분(diff)"이다.**

이 한 문장이 전부다. 나머지는 이걸 가능하게 하는 부품들이다.

## A-1. FormID — 모든 것에 영구 주소가 있다

게임 내 모든 오브젝트는 32비트 고유 식별자 **FormID**를 갖는다.

```
0x 01 A2B3C4
   ~~ ~~~~~~
   │  └─ 하위 24비트: 해당 플러그인 내 레코드 인덱스
   └──── 상위 8비트: 로드 오더상 플러그인 인덱스
```

- `0x00......` → `Fallout4.esm` (로드 오더 0번)
- `0x01......` → 두 번째 플러그인
- `0xFF......` → **런타임에 스크립트로 생성된 동적 오브젝트**
- `0xFExxxyyy` → ESL(라이트 플러그인). `FE` + 12비트 플러그인 + 12비트 레코드 = 4096개 × 4096 레코드

> 💡 **플러그인 255개 제한의 정체가 이것이다.** 상위 바이트가 `0x00`~`0xFE`뿐이고 `0xFF`는 런타임 예약이라, 구조적으로 255개를 넘을 수 없다. ESL은 `FE` 슬롯 하나를 쪼개 쓰는 우회책이다.

핵심은 **이 주소가 세션과 세이브를 넘어 영구적**이라는 것. 오브젝트를 지목할 안정적인 방법이 항상 존재한다.

## A-2. Base Form vs Reference — 템플릿과 인스턴스의 분리

```
TESForm (모든 것의 조상)
  └─ TESBoundObject  ← "베이스 폼": 정의/템플릿
  │    예) ARMO_VaultSuit111 — 메시, 무게, 가치, 방어력
  │
  └─ TESObjectREFR   ← "레퍼런스": 월드에 배치된 개별 인스턴스
       예) 볼트 111 락커 안에 놓인 그 볼트슈트 한 벌
       고유 FormID + 위치/회전/스케일 + 베이스 폼 포인터 + 개별 상태
```

같은 커피잔 500개가 월드에 있다면 → 베이스 폼 1개 + 레퍼런스 500개.
각 레퍼런스는 **자기만의 FormID와 자기만의 상태**를 갖는다. 이게 개별 추적의 전제 조건이다.

## A-3. Persistent vs Temporary 레퍼런스

각 셀(CELL)의 레퍼런스 목록은 플러그인 파일에서 두 블록으로 나뉘어 저장된다.

| | Persistent | Temporary |
|---|---|---|
| 메모리 | **게임 세션 내내 상주** | 셀이 로드될 때만 |
| 용도 | 퀘스트 NPC, 텔레포트 도어, 맵 마커, 스크립트 타겟 XMarker | 대부분의 잡동사니 |
| 비중 | 소수 | 압도적 다수 |

> ⚠️ **흔한 오해:** "Temporary = 저장 안 됨"이 아니다. **메모리에 상주하지 않을 뿐, 변경된 상태는 세이브에 남는다.**

Persistent 레퍼런스의 존재 이유가 중요하다. **로드되지 않은 오브젝트를 어떻게 참조할 것인가**라는 난제를, "항상 필요한 놈은 항상 메모리에 둔다"로 해결한 것이다. 퀘스트 스크립트가 지도 반대편의 NPC에게 명령을 내릴 수 있는 이유다.

## A-4. Change Record — 실제 메커니즘

여기가 핵심이다.

세이브 파일에는 **Change Forms 테이블**이 있다. 각 항목은 이렇게 생겼다:

```
{ FormID, changeFlags(비트필드), 가변길이 데이터 }
```

`changeFlags`가 **어떤 필드가 바뀌었는지**를 비트로 표시하고, 켜진 비트에 해당하는 데이터만 정해진 순서로 직렬화된다. 대표적인 플래그:

| 플래그 | 의미 |
|---|---|
| `CHANGE_REFR_MOVE` | 위치/회전 변경 |
| `CHANGE_REFR_HAVOK_MOVE` | 물리 시뮬레이션 결과로 이동 |
| `CHANGE_REFR_CELL_CHANGED` | 다른 셀로 이동 |
| `CHANGE_REFR_SCALE` | 크기 변경 |
| `CHANGE_REFR_INVENTORY` | 인벤토리 내용물 변경 |
| `CHANGE_REFR_EXTRA_OWNERSHIP` | 소유권 변경 (훔치기 판정용) |
| `CHANGE_FORM_FLAGS` | 활성화/비활성화/삭제 |
| `CHANGE_OBJECT_EXTRA_ITEM_DATA` | 개별 아이템 부가 데이터 |

### 실제 동작

```
커피잔 A: 플레이어가 건드린 적 없음
  → 세이브에 아예 없음. 로드할 때마다 ESM에서 원본 그대로 재구성.
  → 저장 비용 0 바이트

커피잔 B: 플레이어가 테이블에서 떨어뜨림
  → Change Form 1개 생성
     FormID: 0x0012AB34
     flags:  CHANGE_REFR_MOVE | CHANGE_REFR_HAVOK_MOVE
     data:   새 위치(x,y,z) + 회전(rx,ry,rz)
  → 저장 비용 약 30바이트
```

> 🔑 **이 설계의 아름다움:** 저장 비용이 **월드 크기가 아니라 플레이어가 바꾼 양에 비례한다.**
> 오브젝트 500만 개짜리 월드라도, 아무것도 안 건드렸으면 세이브는 거의 비어 있다.
> "모든 걸 저장한다"가 아니라 "**안 바뀐 건 원본에서 다시 읽으면 되니까 저장할 필요가 없다**"는 발상이다.

## A-5. ExtraData — 인스턴스별 확장 속성 백

베이스 폼에 없는 개별 상태는 `TESObjectREFR`에 붙는 **`BSExtraDataList`** (연결 리스트)에 담긴다.

```
TESObjectREFR (그 권총 한 자루)
  └─ BSExtraDataList
       ├─ ExtraOwnership      → 소유자: DiamondCityGuardFaction
       ├─ ExtraCount          → 스택 수량
       ├─ ExtraHealth         → 내구도
       ├─ ExtraInstanceData   → 부착된 개조 부품 목록  ★
       ├─ ExtraTextDisplayData→ 플레이어가 붙인 이름 "쓰레기청소기"
       ├─ ExtraLock           → 자물쇠 난이도, 열쇠 FormID
       ├─ ExtraTeleport       → 연결된 도어의 목적지
       └─ ExtraLinkedRef      → 다른 레퍼런스와의 연결
```

★ **폴아웃 4의 무기 개조 시스템이 성립하는 이유가 `ExtraInstanceData`다.** 총 한 자루 한 자루가 자기만의 부품 조합을 들고 다닐 수 있다.

이건 사실상 **오브젝트마다 붙는 희소(sparse) 컴포넌트 리스트** — ECS가 유행하기 한참 전에 나온 ECS 비슷한 것이다. 필요한 놈만 필요한 속성을 갖는다.

## A-6. 셀 로드/언로드 생애주기

```
[플레이어 이동 → 새 셀이 uGridsToLoad(기본 5×5) 범위 진입]
   1. ESM/ESP에서 그 셀의 temporary 레퍼런스 목록을 읽음      ← 베이스라인
   2. 각 FormID로 세이브의 Change Forms 테이블을 조회
   3. 항목이 있으면 델타를 덮어씀 (위치/인벤토리/소유권/삭제…)
   4. 최종 상태로 3D 메시 로드 + Havok 강체 생성 + Papyrus VM에 등록

[플레이어 이탈 → 셀이 범위 밖]
   1. 변경된 레퍼런스의 상태를 Change Form으로 기록/갱신
   2. 3D·Havok 파괴, 메모리 해제
   3. persistent 레퍼런스는 그대로 메모리 유지
```

물리 처리도 여기 얹힌다. 던진 물건이 Havok에서 굴러다니다 속도 임계값 아래로 잠들면(sleep), 엔진이 그 최종 트랜스폼을 `CHANGE_REFR_HAVOK_MOVE`로 확정 기록한다. 셀이 언로드되면 강체는 사라지지만 좌표는 남는다.

## A-7. 셀 리셋 — 무한 증식을 막는 압력 밸브

전부 영구 보존하면 세이브가 끝없이 커진다. 그래서 **셀 리셋 타이머**가 있다.

- 게임 설정값(`iHoursToRespawnCell` 등, 스카이림 계열 기준 240시간 / 소탕된 던전 720시간)이 지나면
- 엔진이 그 셀의 temporary 레퍼런스 Change Record를 **폐기**하고 ESM 원본으로 되돌린다
- → 적이 리스폰되고 전리품이 다시 채워진다

**단, 워크샵/정착지 셀과 "Never Resets" 플래그가 붙은 셀은 제외된다.**
생츄어리에 떨어뜨린 물건은 영원히 남고 레이더 캠프는 재보급되는 이유가 이것이다.

## A-8. 그런데 왜 세이브가 부푸는가

이 설계에도 새는 구멍이 있다:

1. **동적 생성 오브젝트(`0xFF...`)** — 스크립트가 스폰한 것들은 ESM 베이스라인이 없어 **전체 상태를 통째로 저장**해야 한다
2. **Papyrus VM 상태** — 스크립트 인스턴스의 멤버 변수, 실행 중인 스택, 대기 이벤트가 전부 직렬화된다
3. **고아 레코드** — 모드를 제거하면 그 모드의 FormID를 가리키는 Change Record와 스크립트 인스턴스가 남아 떠돈다
4. **정착지 건설** — 건축물 하나하나가 새 레퍼런스 + 완전한 Change Record. 대형 정착지는 수천 개를 만든다

## A-9. UE5에는 왜 이게 없나

UE5의 모델은 근본적으로 다르다.

| | Creation Engine | Unreal Engine 5 |
|---|---|---|
| 월드의 정체 | **레코드 데이터베이스** (스키마가 있는 DB) | **씬 그래프** (`.umap` 에셋) |
| 오브젝트 ID | FormID (전역·영구·32비트) | 없음. OFPA의 `FActorGuid`가 가장 근접 |
| 런타임 상태 저장 | 엔진 내장 (Change Record) | **없음.** `USaveGame`에 직접 구현 |
| 언로드된 오브젝트 참조 | Persistent 레퍼런스로 해결 | 소프트 레퍼런스 — 해석하려면 로드해야 함 |
| 스트리밍 후 재로드 | 델타 재적용 → 상태 유지 | **새 인스턴스.** 명시적으로 저장 안 한 건 소멸 |
| 삭제 표현 | `CHANGE_FORM_FLAGS`의 삭제 비트 | "이 배치된 액터는 파괴됨"을 직접 기록해야 함 |

UE5의 `USaveGame`은 "저장할 대상을 네가 열거하면 직렬화해 주는 도구"지, "월드가 알아서 변경을 추적하는 시스템"이 아니다. `SaveGame` UPROPERTY 지정자와 `FObjectAndNameAsStringProxyArchive`가 제공되지만, **무엇을 저장할지·어떻게 다시 찾을지는 전부 개발자 몫**이다.

### 폴아웃식 영속성을 UE5에 만들려면

1. **안정적 ID 체계** — OFPA의 `FActorGuid`를 FormID 대용으로 활용 + 런타임 스폰 액터용 ID 발급기(`0xFF` 대응물)
2. **베이스라인 + 델타 직렬화** — 레벨 에셋의 초기 상태를 기준으로 삼고, 언로드 시점에 diff를 떠서 변경분만 저장
3. **World Partition 스트리밍 훅** — 셀 로드/언로드 콜백에 델타 적용·수집을 바인딩
4. **인스턴스별 속성 백** — `BSExtraDataList` 대응물 (컴포넌트 or 태그+데이터 맵)
5. **리셋/리스폰 정책** — 세이브 무한 증식 방지 밸브
6. **물리 정착 감지** — 강체 sleep 시점에 트랜스폼 확정 기록
7. **세이브 버저닝/마이그레이션** — 패치로 베이스라인이 바뀌었을 때의 호환 처리
8. **언로드 상태 시뮬레이션** — 퀘스트·AI가 로드되지 않은 오브젝트를 참조·조작할 수 있어야 함

**그리고 이건 렌더링과 달리 "플러그인 켜면 되는" 종류가 아니다.** 퀘스트, AI, 인벤토리, 물리, 건설 시스템 전부가 이 레이어 위에 얹히기 때문에, 사실상 게임 아키텍처 전체를 규정한다.

## A-10. 정리

> **Creation Engine의 월드는 데이터베이스고, UE5의 월드는 씬 그래프다.**

ESM/ESP는 스키마를 가진 레코드 DB 파일이고, 엔진은 **렌더링도 하는 데이터베이스 엔진**에 가깝다. 그래서:

- **모드 레이어링이 자연스럽다** — 레코드 오버라이드 = DB 행 덮어쓰기. 로드 오더 = 적용 순서
- **영속성이 자연스럽다** — Change Record = 행 단위 diff
- **모든 오브젝트가 1급 시민이다** — 커피잔도 데드클로도 같은 `TESObjectREFR`

UE5로 옮긴다는 건 이 데이터베이스 모델을 버리고 씬 그래프 모델로 간다는 뜻이다. 렌더링은 얻지만 **DB가 공짜로 주던 것들(영속성, 모드 레이어링, 균일한 오브젝트 모델)을 전부 직접 다시 지어야 한다.**

오블리비언 리마스터드가 원본 엔진을 시뮬레이션 레이어로 남긴 이유가 정확히 이것이다. 렌더러는 갈아끼울 수 있어도, **데이터베이스는 갈아끼울 수 없다.**

# 부록 B. 기술 명칭 대조표

부록 A에서 설명한 각 부품의 **일반적인 컴퓨터과학 / 소프트웨어공학 용어**.
베데스다가 발명한 게 아니라, 대부분 다른 분야에서 확립된 기법을 게임 월드에 적용한 것이다.

## B-1. 전체 아키텍처의 정식 명칭

한 문장으로 말하면:

> **공간 페이징을 적용한, Copy-on-Write 기반 베이스라인+델타 영속 객체 데이터베이스**
> *(Baseline-plus-delta persistent object database with copy-on-write semantics and spatial paging)*

구성 개념 셋:

| 개념 | 정식 용어 | 설명 |
|---|---|---|
| ESM = 읽기 전용 원본, 세이브 = 덮어쓰기 레이어 | **Copy-on-Write (CoW)** / **Overlay(Union) 레이어링** | 수정 전엔 원본 공유, 수정 순간에만 사본 생성 |
| 안 바뀐 건 저장 안 함 | **델타 인코딩 (Delta Encoding)** / **차분 저장** | 기준본 대비 변경분만 기록 |
| 모든 오브젝트가 영구 ID로 자동 보존 | **직교 영속성 (Orthogonal Persistence)** | 타입·위치와 무관하게 균일하게 적용되는 영속성 |

## B-2. 부품별 대조표

| 폴아웃 4의 부품 | 정식 기술 명칭 | 같은 기술을 쓰는 다른 사례 |
|---|---|---|
| **FormID** | **OID (Object Identifier)** / 대리키(Surrogate Key) / 영속 핸들 | 객체지향 DB의 OID, ECS의 Entity ID, UUID |
| **베이스 폼 ↔ 레퍼런스** | **Type Object 패턴** (근접: Flyweight, Prototype) | 『Game Programming Patterns』의 Type Object. 내재 상태/외재 상태 분리 |
| **Change Record** | **델타 인코딩** + **필드 단위 더티 트래킹** | git 팩파일 델타 압축, rsync, 비디오 코덱 |
| **changeFlags 비트필드** | **더티 비트 / 더티 플래그 (Dirty Bit)** | ORM의 변경 추적, OS 페이지 테이블의 dirty bit |
| **ESM(원본) + 세이브(델타)** | **I-프레임 / P-프레임** 구조 | H.264 등 영상 코덱의 키프레임 + 차분 프레임 |
| **BSExtraDataList** | **프로퍼티 백 (Property Bag)** / 희소 컴포넌트 저장 | ECS의 sparse set, 이종(heterogeneous) 속성 리스트 |
| **Persistent vs Temporary 레퍼런스** | **고정(Pinned) vs 페이지 가능(Pageable)** | OS 가상 메모리의 pinned page, DB 버퍼풀 고정 |
| **셀 그리드 + uGridsToLoad** | **균일 공간 분할 (Uniform Spatial Partition)** + **페이징** | 타일맵 스트리밍, 옥트리/그리드 컬링 |
| **셀 로드 시 델타 적용** | **하이드레이션 (Hydration / Rehydration)** | ORM 엔티티 하이드레이션, SSR 프론트엔드 하이드레이션 |
| **셀 리셋 타이머** | **TTL 기반 캐시 축출 (TTL Eviction)** | Redis TTL, HTTP 캐시 max-age |
| **로드 오더 레코드 오버라이드** | **LWW(Last-Write-Wins) 계층 병합** / 캐스케이딩 오버라이드 | CSS 캐스케이드, Docker 이미지 레이어, kustomize 오버레이 |
| **Havok 정지 후 좌표 확정** | **강체 슬리핑 / 비활성화 (Rigid Body Deactivation)** | 모든 물리 엔진의 sleep threshold |
| **베이스라인 공유** | **구조적 공유 (Structural Sharing)** | 영속 자료구조(persistent data structure), 불변 컬렉션 |
| **ESM/ESP 파일 자체** | **스키마 기반 레코드 데이터베이스** | 사실상 OODBMS 파일 포맷 |

## B-3. 특히 정확한 비유 세 가지

### ① OverlayFS / Docker 이미지 레이어

```
┌────────────────────────────┐
│ 세이브 파일 (Change Forms) │  ← 쓰기 가능 레이어 (upperdir)
├────────────────────────────┤
│ 모드 ESP들 (로드 오더순)   │  ← 읽기 전용 레이어들
├────────────────────────────┤
│ Fallout4.esm               │  ← 읽기 전용 베이스 (lowerdir)
└────────────────────────────┘
```

파일을 수정하면 상위 레이어로 **copy-up**되고, 안 건드린 파일은 하위 레이어에서 그대로 읽는다.
Creation Engine은 **파일 대신 레코드 단위로 이걸 한다.** 개념적으로 완전히 동일하다.

### ② 영상 코덱의 I-프레임 / P-프레임

- **ESM = I-프레임(키프레임)** — 완전한 원본 상태
- **세이브 = P-프레임(차분 프레임)** — "직전 대비 뭐가 바뀌었나"만 기록

영상이 매 프레임 전체 화면을 저장하지 않듯, 세이브도 매번 월드 전체를 저장하지 않는다.

### ③ OS 가상 메모리

| 폴아웃 4 | OS |
|---|---|
| 셀(Cell) | 페이지(Page) |
| uGridsToLoad 범위 | 레지던트 셋(Resident Set) |
| Persistent 레퍼런스 | 고정 페이지(Pinned Page) — 스왑 아웃 금지 |
| 셀 언로드 시 델타 기록 | 더티 페이지 write-back |
| changeFlags | 페이지 테이블의 dirty bit |

## B-4. UE5 쪽 용어

| 항목 | UE5의 정식 명칭 |
|---|---|
| 저장 시스템 | **명시적 객체 그래프 직렬화** (`USaveGame`, `FArchive`) |
| 저장 대상 지정 | `SaveGame` UPROPERTY 지정자 — **옵트인(opt-in) 직렬화** |
| 직렬화 도구 | `FObjectAndNameAsStringProxyArchive` — **프록시 아카이브 패턴** |
| 액터 영구 ID | `FActorGuid` (OFPA) — FormID에 가장 근접한 대응물 |
| 로드 없이 읽는 메타데이터 | `FWorldPartitionActorDesc` — **액터 디스크립터** |
| 스트리밍 | **World Partition** — 공간 분할 + 스트리밍 소스 기반 |

**UE5에 없는 것의 정식 명칭:**
- 엔진 레벨의 **자동 더티 트래킹 (automatic dirty tracking)**
- **베이스라인 대비 델타 영속화 (baseline-relative delta persistence)**
- **직교 영속성 (orthogonal persistence)**

UE5는 "무엇을 저장할지 개발자가 열거하는" **옵트인 직렬화**고, Creation Engine은 "모든 변경이 자동 추적되는" **직교 영속성**이다. 이 축이 근본적으로 다르다.

## B-5. 왜 이 명칭이 중요한가

용어를 알면 **UE5에서 이걸 만들 때 무엇을 검색해야 하는지**가 명확해진다.

구현 시 필요한 기법의 정식 명칭:
1. **Persistent Object Identity** — 세션 간 안정적 ID (`FActorGuid` + 런타임 ID 발급기)
2. **Dirty Tracking** — 프로퍼티 변경 감지 (UE5는 `FProperty` 리플렉션으로 구현 가능)
3. **Delta Serialization** — 레벨 에셋 기본값 대비 diff (`FArchive`의 델타 직렬화 모드 활용 가능)
4. **Hydration Hook** — World Partition 셀 로드/언로드 콜백 바인딩
5. **TTL Eviction Policy** — 세이브 무한 증식 방지
6. **Save Schema Versioning / Migration** — `FCustomVersion`으로 처리

> 참고: UE5의 네트워크 리플리케이션(`FRepState`, `NetSerialize`)은 이미 **델타 직렬화 + 더티 트래킹**을 하고 있다.
> 다만 그건 **프레임 단위 네트워크 동기화용 휘발성 델타**지, **디스크 영속화용 델타**가 아니다.
> 개념은 있는데 용도가 달라서 그대로 못 쓴다 — 하지만 참고 구현으로는 매우 유용하다.

# 부록 C. 하이브리드 방식에서 모드 생태계는 어떻게 되는가

13장의 하이브리드(오블리비언 리마스터드 방식)를 폴아웃 4에 적용했을 때, 기존 모드가 어떻게 되는지.

## C-0. 판정 기준 — 이 한 줄로 전부 예측된다

> **모드가 "데이터베이스 위"에 있으면 산다. "렌더러 위"에 있으면 죽는다.**

하이브리드는 렌더러만 갈아끼우고 Creation Engine의 레코드 DB를 그대로 남긴다.
부록 A/B에서 본 것처럼 **모드 레이어링은 DB 기능(레코드 오버라이드)** 이므로, DB가 살아있는 한 그 위의 모드도 산다.
반대로 렌더링·UI·엔진 훅에 의존하는 모드는 기반이 통째로 사라진다.

```
┌────────────────────────────────┐
│  Unreal Engine 5               │ ← 렌더/UI/오디오
│  ✗ 텍스처·메시 리플레이서 죽음  │    여기 얹힌 모드는 전멸
│  ✗ ENB, Scaleform UI 모드 죽음  │
├────────────────────────────────┤
│  Creation Engine (원본)        │ ← 게임로직/DB/영속성
│  ✓ ESP/ESM 플러그인 생존        │    여기 얹힌 모드는 생존
│  ✓ 퀘스트·밸런스·NPC 모드 생존  │
└────────────────────────────────┘
```

## C-1. 살아남는 것 (DB 레이어)

| 모드 종류 | 예시 | 이유 |
|---|---|---|
| 밸런스/수치 조정 | 데미지, 레벨드 리스트, 퍽 개편 | 순수 레코드 데이터 |
| 퀘스트 모드 | 기존 에셋 활용 신규 퀘스트 | 레코드 + Papyrus |
| NPC / 동료 추가 | 기존 메시 재활용 캐릭터 | 레코드 + 대사 |
| 대화·팩션 수정 | 대사 트리, 팩션 관계 | 레코드 |
| 크래프팅 레시피 | 제작대 항목 추가 | 레코드 |
| 게임플레이 규칙 | 생존 난이도, 경제 조정 | 게임 설정 레코드 |

**같이 살아남는 인프라:**
- **로드 오더 / 레코드 오버라이드 / 충돌 해소** — 모딩 패러다임 전체
- **xEdit(FO4Edit), Creation Kit** — 레코드 편집 도구
- **Papyrus 스크립트와 VM**
- **Mod Organizer 2 / Vortex** 같은 플러그인 관리자

> 이게 하이브리드의 최대 세일즈 포인트다. 순수 UE5 리메이크가 모드 생태계를 **100% 날리는** 반면, 하이브리드는 **게임플레이 모드를 통째로 보존한다.**

## C-2. 죽는 것 (렌더러 레이어)

| 모드 종류 | 예시 | 왜 죽나 |
|---|---|---|
| **텍스처 리플레이서** | Vivid Fallout, 4K 텍스처팩 | UE5는 BA2의 DDS를 안 읽음. `.uasset`을 읽음 |
| **메시 리플레이서** | 무기·방어구 모델 교체 | NIF 포맷을 UE5가 안 씀 |
| **ENB** | ENBSeries 프리셋 전부 | ENB는 원본 `d3d11.dll`을 후킹. UE5는 DX12 |
| **UI 모드** | DEF_UI, Better Console, HUDFramework | Scaleform(Flash) → UMG. 기반 자체가 사라짐 |
| **`.ini` 그래픽 튜닝** | `Fallout4Prefs.ini` 설정 | UE5의 `Engine.ini`/`Scalability.ini`로 대체 |
| **F4SE 의존 모드** ★ | MCM, Looks Menu, Buffout 4 등 대다수 대형 모드 | 실행 파일이 통째로 다름 → 스크립트 익스텐더 **전면 재작성** 필요 |

★ **F4SE 문제가 가장 아프다.** 스크립트 익스텐더는 특정 빌드의 메모리 주소에 훅을 거는 방식이라, 실행 파일이 바뀌면 무조건 처음부터 다시 만들어야 한다. 그리고 상위권 인기 모드 상당수가 F4SE에 의존한다.
(오블리비언 리마스터드에서도 스크립트 익스텐더가 커뮤니티 손으로 다시 만들어지기까지 시간이 걸렸다. 결국 되긴 되지만 **하드 리셋**이다.)

## C-3. 애매한 것 — "이음새(seam)" 문제 ★ 여기가 진짜 쟁점

가장 중요한 구조적 문제는 **레이어가 두 개라서, 신규 콘텐츠는 양쪽에 다 들어가야 한다**는 것이다.

```
신규 무기 모드를 설치하면:

  [Creation Engine 쪽]  ESP가 WEAP 레코드 등록  ✓ 정상
  [UE5 쪽]              대응하는 렌더링 에셋 없음 ✗

  → 인벤토리엔 뜨는데 손에 안 보이거나 플레이스홀더로 표시
```

| 모드 종류 | 상태 | 필요한 작업 |
|---|---|---|
| 신규 무기/방어구 | ⚠️ 반쪽 | ESP는 살고, 메시·텍스처는 UE5 pak으로 다시 패키징 |
| 정착지 건축 확장 | ⚠️ 반쪽 | 위와 동일 |
| 날씨·조명 모드 | ⚠️ 반쪽 | 날씨 레코드는 살지만 실제 렌더링은 Lumen이 결정 |
| 애니메이션 모드 | ⚠️ 불확실 | 애니메이션 재생 주체가 어느 레이어냐에 따라 갈림 |
| **Fallout London 급 총괄 모드** | ⚠️ 대공사 | 퀘스트·월드 데이터는 살고, 커스텀 에셋 전부 재작업 |

**즉 하이브리드에서 모딩은 "이중 작업"이 된다.** 게임플레이는 Creation Kit에서, 비주얼은 언리얼 툴에서. 진입 장벽이 올라간다.

## C-4. 새로 생기는 것

죽기만 하는 건 아니다. **모딩 표면이 두 개**가 되면서 새 가능성이 열린다.

| 새 수단 | 내용 |
|---|---|
| **Pak 모드** | UE5 표준 모드 패키징. 에셋 교체·추가 |
| **UE4SS** | 언리얼 게임용 Lua 스크립팅 훅 — 사실상 "UE판 스크립트 익스텐더" |
| **Blueprint 모드** | 로직을 UE 측에서 주입 |
| **ReShade** | ENB는 죽지만 ReShade는 DX12를 지원하므로 생존 |
| **고품질 에셋 모딩** | Nanite 메시, Lumen 대응 머티리얼 — 원본 엔진에선 불가능했던 수준 |

**결론:** 하이브리드는 모드 생태계를 **절반 살린다.**
살아남는 절반이 하필 **가장 만들기 어렵고 대체 불가능한 쪽(퀘스트·세계관·게임플레이)** 이고,
죽는 절반은 **재작업이 가능한 쪽(에셋·비주얼)** 이라는 점에서 트레이드오프로는 유리하다.

다만 **F4SE 의존 모드의 전멸**은 체감상 가장 큰 손실이며, 커뮤니티가 스크립트 익스텐더를 다시 세우기 전까지는 상위권 모드 상당수가 공백 상태가 된다. 오블리비언 리마스터드가 실제로 겪은 과정이 정확히 이것이다.
