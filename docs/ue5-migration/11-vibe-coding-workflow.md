# 11. 바이브 코딩으로 UE5 개발하기

AI에게 코드를 맡기며 진행할 때, UE5는 웹/앱 개발과 조건이 꽤 다릅니다.
**할 수 있는 것과 없는 것을 먼저 알고 시작해야** 헛돌지 않습니다.

## 11.1 AI가 할 수 있는 것 / 없는 것

| 작업 | 가능 여부 | 이유 |
|---|---|---|
| C++ 클래스 작성 (게임플레이 로직, 컴포넌트, 서브시스템) | ✅ 잘 됨 | 텍스트 파일 |
| `.Build.cs`, `.uproject`, `Config/*.ini` | ✅ 잘 됨 | 텍스트 파일 |
| 셰이더 코드(HLSL), 콘솔 명령, 빌드 스크립트 | ✅ 잘 됨 | 텍스트 파일 |
| **Blueprint 편집** | ❌ 불가 | `.uasset`은 바이너리. 텍스트로 만들 수 없음 |
| **머티리얼 그래프** | ❌ 불가 | 동일 |
| **레벨 배치, 라이팅** | ❌ 불가 | 동일 |
| **애님 블루프린트, Niagara** | ❌ 불가 | 동일 |
| 컴파일·실행·디버깅 | ❌ 직접 못 함 | 엔진이 있는 사용자 PC에서만 |

여기서 나오는 결론이 하나 있습니다.

> **로직은 최대한 C++에 두고, 에디터 작업은 "연결"만 남기십시오.**

블루프린트에 로직을 넣으면 AI가 손댈 수 없어 매번 직접 노드를 만져야 합니다.
반대로 C++ 컴포넌트로 만들어 두면 에디터에서는 **컴포넌트를 붙이고 값을 조정하는
것만** 하면 됩니다. 이 프로젝트의 `UExposureComponent`가 그 예입니다 — 에디터
작업은 "캐릭터에 컴포넌트 추가" 한 줄이 전부입니다.

## 11.2 진행 리듬

한 번에 큰 덩어리를 요청하면 컴파일 오류가 무더기로 나오고, 어디서부터 잘못됐는지
알 수 없게 됩니다. **작게 자르고 매번 컴파일**하는 편이 결과적으로 훨씬 빠릅니다.

```
1. "X 기능을 하는 컴포넌트를 만들어줘"     → AI가 .h/.cpp 작성
2. 빌드                                    → 사용자
3. 오류가 나면 메시지를 그대로 붙여넣기     → AI가 수정
4. 에디터에서 붙이고 디버그 표시로 확인     → 사용자
5. "값이 이렇게 나오는데 이상해" 피드백     → AI가 조정
6. 다음 기능으로
```

**3번이 핵심입니다.** UE5 API는 버전마다 시그니처가 조금씩 달라서 AI가 쓴 코드가
한 번에 컴파일되지 않는 경우가 흔합니다. 오류 메시지를 요약하지 말고 **그대로
복사해서 주십시오.** 파일명과 줄 번호가 있어야 정확히 고칠 수 있습니다.

## 11.3 요청을 잘 하는 법

**나쁜 요청**: "스텔스 시스템 만들어줘"
→ 범위가 무한합니다. 빛? 소리? AI? 어디까지가 완성인지 알 수 없습니다.

**좋은 요청**: "경비가 플레이어를 볼 때 노출값에 따라 감지 게이지가 차오르게 하고,
게이지가 1이 되면 경계 상태로 바뀌게 해줘. 기존 `UExposureComponent`의
`GetExposure()`를 쓰고, 게이지 상승 속도는 에디터에서 조정 가능하게."
→ 입력, 출력, 기존 코드와의 연결, 튜닝 지점이 명확합니다.

특히 **"에디터에서 조정 가능하게"** 를 습관적으로 붙이십시오. 수치를 코드에
하드코딩하면 값 하나 바꿀 때마다 재컴파일(수 분)이 필요하지만, `UPROPERTY`로
빼면 플레이 중에도 바꿀 수 있습니다.

## 11.4 이 프로젝트에서 지킬 규칙

- **디버그 표시를 먼저 만든다.** 눈에 안 보이는 값(노출도, 감지 게이지, 소음
  반경)은 화면에 그려지기 전까지 튜닝할 수 없습니다. 기능보다 디버그 뷰가 먼저입니다.
- **한 번에 한 시스템.** 빛 감지가 만족스러워지기 전에 소음을 시작하지 마십시오.
  두 시스템이 동시에 불완전하면 어느 쪽이 문제인지 판단할 수 없습니다.
- **회색 박스로 먼저.** 자산 추출은 뒤로 미루십시오. UE5 기본 도형과 매네퀸으로
  재미있으면 자산을 붙여도 재미있고, 그 반대는 성립하지 않습니다.
- **컴파일이 깨진 상태로 다음 요청을 하지 않는다.** 오류가 쌓이면 원인 추적이
  기하급수적으로 어려워집니다.

## 11.5 자주 막히는 지점

| 증상 | 원인 |
|---|---|
| `unresolved external symbol` | `.Build.cs`의 `PublicDependencyModuleNames`에 모듈 누락 |
| `GENERATED_BODY` 관련 오류 | `.generated.h`가 헤더의 **맨 마지막** include가 아님 |
| UENUM/델리게이트 오류 | 델리게이트가 참조하는 타입이 아직 선언되지 않음 (순서 문제) |
| 에디터에서 C++ 클래스가 안 보임 | 빌드는 됐지만 에디터를 재시작하지 않음 |
| 값이 항상 0 | 컴포넌트를 액터에 실제로 추가하지 않음 |
| 간헐적 크래시 | 오브젝트 포인터에 `UPROPERTY()` 누락 → GC가 수거 |

마지막 항목은 03 문서에도 적어 두었지만, 바이브 코딩에서 특히 위험합니다.
재현이 어려워서 원인을 찾기 힘들고, AI에게 "가끔 크래시 나"라고만 말하면
고칠 수 없기 때문입니다. **크래시 콜스택을 통째로 주십시오.**
